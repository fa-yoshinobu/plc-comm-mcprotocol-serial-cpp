# 4C ASCII Format4 Native Extension Analysis Packet

Status: resolved 2026-07-02. The native-extended issue was a client encoder bug
(missing trailing ASCII device-modification field); the fix is verified on live
iQ-R and Q/L targets. This packet is kept as the analysis and verification
record.

## Purpose

This document summarizes the 4C ASCII Format4 communication issue seen with
native extended devices, the desk analysis that identified the root cause, and
the post-fix hardware verification on both target families.

The issue is not that all Format4 communication fails. Plain device access
worked in the observed runs. The failing area is native extended access:

- Link-direct devices: `Jn\X`, `Jn\Y`, `Jn\B`, `Jn\W`, `Jn\SB`, `Jn\SW`
- Native-qualified unit/CPU-buffer devices: `Un\G`, `Un\HG`

Password handling is a separate command-family topic. The Format4 symptoms in
this record are explained by serial-module format selection and request-frame
shape, not by PLC password state.

## Root cause identified (2026-07-02)

Desk analysis against SH-080003-AF answered the analysis questions below. The
failure is a client-side encoder bug, not a target or serial-module limitation.

### Finding

In ASCII code, the device extension specification must end with a trailing
device-modification field after the device number: 3 ASCII `0` characters for
the MELSEC-Q/L subcommands, 4 for the MELSEC iQ-R subcommands. SH-080003-AF
appendix 1 shows this in the message-format diagrams (p.430 for `Jn\`, p.432
for `Un\G`) and in the worked example on p.431:

```text
manual example (J1\W100, subcommand 0080):
0080 00 J001 000 W* 000100 000            <- trailing 000 present

observed frame (J1\SB10, subcommand 0083):
0083 00 J001 0000 SB** 0000000010 0001    <- trailing 0000 missing;
                                             points field follows directly
```

The observed frames end the extended device specification at the device
number. `src/codec.cpp` confirms the omission:
`append_link_direct_device_reference_ascii` and
`append_extended_device_reference_ascii` emit `00` + `J`/`U` + 3 hex digits +
modification (3/4 digits) + device code + device number and stop; there is no
trailing `append_device_modification_ascii` call. The binary encoders emit the
full layout (`00 00` + device number + device code + `00 00` + network/module
number + `F9H`/`F8H`), which is why Binary Format5 succeeds on the same
targets.

### Why this matches every observation

- `7F22H` is generated by the C24 itself, before CPU forwarding. The
  SH-081249-L error list classifies `7F22H` as a command error detected while
  parsing the received message (PRO category). With the 3/4-character shift,
  the C24 reads CR LF where the points field should be and rejects the frame
  as an invalid command/device.
- The single `J1\W0` write timeout also fits: write requests carry data after
  the device specification, so the short frame leaves the C24 waiting for the
  missing characters.
- Plain devices pass because they do not use the extension layout. iQ-R and
  Q/L targets fail identically because both go through the same encoder path.

### Manual answers

1. Yes. ASCII Format1-4 supports the extension specification; SH-080003-AF
   p.430/p.432 documents the ASCII message formats for `Jn\` and `Un\G`.
2. Subcommands `0080`/`0081`/`0082`/`0083` are valid in ASCII as well as
   binary (p.430 command/subcommand table).
3. `7F22H` came from the serial communication module (PRO parse error), not
   from the CPU after forwarding.
4. No such setting was found, and none is needed to explain the evidence.
5. `Jn\` and `Un\` use the same extension layout, differing only in the
   `J`/`U` marker; both were affected by the same missing field.

### Fix and verification status

- Implemented fix: the trailing device-modification field (3/4 `0` characters,
  `append_device_modification_ascii`) is now appended after the device number
  in both ASCII extended-reference builders in `src/codec.cpp`.
- Request-shape tests cover the Q/L manual example and iQ-R `Jn\...` / `Un\G`
  shapes.
- A post-fix iQ-R hardware recheck confirmed `Un\G` and `Un\HG` reads in
  Format4 ASCII. An interim `Jn\...` NG observation (partial response, then
  stop) was traced to a stale pre-fix CLI binary; see the stale-build note in
  the hardware recheck section. With rebuilt post-fix binaries, all `Jn\...`
  read and write routes passed on the same target and session.

## Current conclusion

Resolved on 2026-07-02 for both target families: the failure was the client
encoder bug above, not a target or serial-module limitation. With the fixed
encoder, ASCII Format4 native extended access (`Jn\...`, `Un\G`, `Un\HG`)
passed read, write, random, multi-block, and monitor checks on the live iQ-R
target (`R120PCPU`, subcommands `0082`/`0083`) and the live Q/L target
(`Q06UDVCPU`, subcommands `0080`/`0081`). Every access in the original NG
lists was re-run and passed. No follow-up remains for this issue.

Do not block ordinary plain-device Format4 traffic based only on this issue.
On 2026-07-02, after the Q serial module was intentionally set to MC Protocol
Format4, a fresh `melsec:qcpu` control check read `D0` and `cpu-model`
successfully on `Q06UDVCPU`. This confirms that current basic Q Format4
communication works when the module setting and CLI frame mode match.

### Stale-build reproduction of the interim `Jn\...` NG

An interim recheck recorded `J1\X10` / `J1\W10` as NG ("response stopped
midway"). That run used a stale pre-fix CLI binary (`build/Release`, built
before the codec fix). The stale binary was re-run deliberately in the same
session for confirmation:

| Binary | `J1\X10` read | `U3E0\G10` read | TX length |
| --- | --- | --- | --- |
| Pre-fix (`build/Release`, 05:36) | timeout / stalls | NAK `7F22H` | 55 chars, no trailing `0000` |
| Post-fix (rebuilt) | OK | OK | 59 chars, trailing `0000` present |

This is direct hardware confirmation of the root cause. After the stale-binary
timeout, `recover-c24 eot` restored the line as expected. All of
`build/Release`, `build/Debug`, and `build_win` were rebuilt post-fix on
2026-07-02; check the CLI binary timestamp before trusting any new NG
observation.

## Raw-frame finding

The `J1\SB10` Format4 ASCII read trace was decoded byte-by-byte. The frame had
the expected high-level shape:

```text
ENQ
F8
00 00 FF 03FF 00 00
0401
0083
00
J001
0000
SB**
0000000010
0001
CR LF
```

The response was:

```text
NAK
F8 00 00 FF 03FF 00 00
7F22
CR LF
```

The PLC/serial module appears to have received and parsed the frame far enough
to echo the route fields and return a structured `7F22H` end code. No obvious
field shift, width mismatch, or missing Format4 terminator was found in this
trace.

Correction (2026-07-02): the re-review against SH-080003-AF p.430-431 found
that the frame above is 4 characters short. The extended device specification
must end with a trailing device-modification field (`0000` for iQ-R
subcommands) between the device number and the points field. See "Root cause
identified" above.

## Manual facts already checked

- SH-081249-L lists `7F22H` as an MC protocol command error. Although the error
  table includes remote-password length among possible causes, these Format4
  traces did not send remote-password commands. Treat password analysis as the
  separate `1630` / `1631` hold, not as a cause of this Format4 issue.
- The working interpretation is invalid command/subcommand/device from the
  serial module's point of view when the pre-fix frame omitted the trailing
  device-modification field.
- SH-080003-AF examples and field layouts were used as the frame-shape check
  baseline. Re-review found the missing trailing device-modification field
  after the device number.

## Resolved hypothesis

Resolved 2026-07-02: the remaining encoder/client bug hypothesis is confirmed.
The known defect was the missing trailing ASCII device-modification field. Any
remaining rejection after this fix must be treated as new hardware evidence and
diagnosed from fresh raw TX/RX captures.

## Operational decision

- Format4 ASCII native extended access (`Jn\...`, `Un\G`, `Un\HG`) is verified
  post-fix on both iQ-R and Q/L targets, including representative reads,
  writes with readback/restore, random, multi-block, and monitor routes. The
  Binary Format5 restriction for these routes is lifted.
- Pre-fix Format4 ASCII observations remain maintainer evidence only. Always
  confirm the CLI binary is post-fix before recording new evidence.
- Public support tables can claim Format4 ASCII support for the native
  extended routes on the validated Q/L and iQ-R families.
- Plain-device Format4 behavior is not blocked by this issue. Continue treating
  it as ordinary profile coverage rather than as part of native-extension
  failure analysis.
